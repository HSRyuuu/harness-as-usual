# v1.1.0 — Autopilot, And Investigations That Carry On

**Date:** 2026-08-27 · **Previous:** 1.0.0 (2026-08-25)

Two changes, both at the prompt layer, both about a path the harness made harder
than it needed to be. `scripts/` is untouched by either — no new event kind,
phase, approval action, or vocabulary value, and the record tests are unchanged.

- **Autopilot.** A user can tell AsUsual to stop asking permission to continue.
  The harness runs to the next real gate and says up front how many stops remain.
- **Investigations that carry on.** An `issue` that finishes and turns out to need
  the work done can become the `topic` or `direct-work` in place, instead of
  spawning a second folder and a link.

---

# Part 1 — Autopilot

This is the second attempt at the idea. The first — the 0.2.2 auto mode — was
reverted in 0.2.3. Much of this half is about why this one is not that one.

## What Was Added

One section: `as-usual-rules/core-rules.md` §10. Four skills reference it.

### Hard gates and soft stops

The section names a distinction the tree never wrote down. Three points in a
pipeline are refused by `as-usual-record.py` unless recorded as `--actor user` —
execution approval, a fresh high-risk approval, the git action choice. Every other
pause exists only as a sentence in a skill.

Autopilot suppresses the second kind and nothing else. The consequence is stated
rather than hidden: **a fully automatic `topic` still stops twice**, plus once per
high-risk operation. When a user asks for "the whole thing", the harness answers
with that number.

One honest asterisk, carried over from §4: `finalize` seals the record before
`git-action` runs, so that last choice usually falls outside the script's reach
and rests on the user's stated choice and on git history.

### Turning it on

- `autopilot` — run to the next hard gate.
- `autopilot:<phase>` — stop earlier, at a phase the unit actually uses.
- Prose counts. The instruction arrives as "run to the plan, stop asking" as often
  as it arrives as a flag.

Only the user turns it on, and it lasts for the session. It is deliberately **not**
written into `contexts.md` frontmatter: a resumed session starts manual, because a
"do not ask me" found in a file is an earlier agreement, and §8 already says those
do not waive a gate.

### The stop guard

Two things are stops, not decisions:

- **Anything that needs approval.** Beyond the three gates: if you are weighing
  whether an action needs approval, that hesitation is the answer. An action whose
  cost lands outside the repository — a deploy, an external call, another team's
  work, money — counts.
- **Any fact that could not be checked.** Before deciding, the agent must be able
  to cite what it checked: a file and line, a command and its output, a document.
  Nothing to cite is a stop. The moment "probably" is about to enter an artifact is
  that moment.

The boundary that keeps this usable: an unchecked fact the work does not depend on
is a `note`, not a stop. The test is whether the output is wrong if the fact is
wrong.

Optional steps follow their owner's matrix rather than a blanket default — a step
marked *proposed by default* runs, one marked *optional* runs only when the
matrix's own condition is met, and `cleanup-code` is never auto-approved.
`finalize` is the exception: a unit autopilot carried to the end is finalized,
because that is where the record's completeness is checked and an unattended run
needs the check more than an attended one.

### Record honesty

Turning it on records one `decision` with `--data autopilot=on`, and every judgment
made under it carries the same `--data`. The actor is `claude` or `codex` — never
`user`. In `contexts.md` those entries are marked `(autopilot)`.

At each hard gate the agent presents the autopilot decisions made since the previous
gate as one block, so a single approval covers the artifact and the judgments behind
it, and one rejection reopens the step that produced it. `report.md` carries the
ones made after the plan gate.

## How This Differs From The 0.2.2 Auto Mode

The revert in 0.2.3 gave two reasons. Reviewing the removed file turned up a third
that was never written down.

| 0.2.2 auto mode | 1.1.0 autopilot |
| --- | --- |
| A fourth runtime rules file | One section inside `core-rules.md`; the contract is still three files |
| Answered the user's decisions, including execution approval | Crosses no `--actor user` gate; only the prompt-level "stop and wait" |
| `mode: auto` in `contexts.md` frontmatter, so resumed sessions inherited it | Session-scoped; a resume starts manual |
| Silent on how a judgment was justified | Every `(autopilot)` decision must cite the evidence it checked, or it is a stop |

The third reason: **as written, that mode could not have run.** Its table told the
agent to record `approval --action execution` itself; its own Record Honesty section
forbade `--actor user` for a decision the user did not make; and
`gates.py:_check_user_decision` refuses every approval that is not
`--actor user --status success`. Reaching the execution gate in that mode meant
either a script refusal or a false record. Naming the hard gates as uncrossable is
what makes this version implementable at all.

# Part 2 — Investigations That Carry On

Nothing in the script changed here either — the path was already legal and no skill
could reach it.

## The Path That Was Already There

`move` relabels a work folder in place, and the gate refuses it only once the
folder has produced `requirements.md`, `plan.md`, or `conclusion.md`.
`MOVE_TARGETS` has always included `topic` and `direct-work`. So `issue → topic`
was legal from the day the three units shipped.

Three sentences at the prompt layer kept it unreachable:

- `core-rules.md` §7 said `move` exists for *exactly one* situation — the unit
  was chosen wrongly. An investigation ending in work is not that.
- `run-issue` wrote `conclusion.md` first, finalized, and only then offered the
  follow-up. By the time the offer arrived, the gate had closed on itself.
- No skill called `move` outside an `inbox` folder.

The result was a tax nobody chose: every investigation that led to work paid for a
second folder, a two-way link, and a `conclusion.md` transcribed into
`requirements.md`.

## What Changed

### `move` has two situations

`core-rules.md` §7 now states both, as the same fact — the folder has produced no
output, so its label is still open:

- Gathering revealed the unit was chosen wrongly.
- An investigation finished and the **same scope** carries straight on into the
  work, before `conclusion.md` is written.

Past that point the answer is still always a link. A concluded issue does not
become the follow-up topic.

### `run-issue` asks before it writes

`Concluding` used to have one ending. It now presents three, once:

```text
1. conclusion only  — the question is answered. Nothing gets built now.
2. carry on         — the same scope becomes the work. This folder changes unit.
3. split            — the finding opens several separate pieces of work.
```

Ending 1 remains the expected one. Confirming a cause and stopping there is a
normal ending, and the skill says so where the choice is presented rather than in a
footnote.

Ending 2 runs `move`, then records a handoff entry. That entry is not bookkeeping:
`move` carries no phase, so without it `status` keeps deriving `investigating` on a
folder that is now a `topic` — a phase that unit does not use, on the exact call a
resuming session reads first.

Ending 2 also does **not** write `conclusion.md`. What was found is already in
`contexts.md` and in the confirmed entries, which is what `write-requirements`
reads. The transcription step is gone rather than automated.

### `conclusion.md` gains an optional Decomposition table

For ending 3 only:

| # | Unit & slug | Scope | Depends on | Covers |

Every finding lands in exactly one row; a row covering nothing is not follow-up
work. **Scope** is what each follow-up's `contexts.md` boundary is copied from, so
two rows never claim the same files.

It exists because `link` records a follow-up only once that folder is created. A
follow-up that was identified and never created left no trace anywhere — the one
thing AsUsual exists to prevent. Rows the user declines stay in the table with the
reason, so a later session does not re-propose them as new.

**No gate reads this table.** It is a recommendation that survives the session, not
an obligation, and the skill says so in those words. Raising it to a contract would
take `status` learning to read it; that is not in this release.

# What To Do Differently

**Users**

- Say `autopilot` (or just ask it to stop checking in) when you want the run to
  carry itself to the plan or to the end. Read the decision block at the gate —
  that is where everything decided in your place is handed back to you.
- When an investigation lands and you want the fix built, you will be asked which
  of the three endings applies instead of being handed a conclusion and a new
  folder. Picking "carry on" keeps one folder and one path; stopping at the
  conclusion is still a normal answer.

**Maintainers**

- `verify-runtime-workflow-consistency` gained check 11. It asserts the autopilot
  rule has one owner, that no skill restates the gate list, and that nothing
  anywhere instructs the agent to record an approval on the user's behalf.
- `move` is no longer inbox-only. A skill that documents unit transitions has to
  describe both situations, and `run-issue` is now its second caller.
