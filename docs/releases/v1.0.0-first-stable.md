# v1.0.0 — First Stable Release

**Date:** 2026-08-25 · **Previous:** 0.3.0 (2026-08-21)

1.0.0 fixes the surface AsUsual has been converging on since the first commit on
2026-06-28. The three work units, the seven core rules, the single record
helper, and the fourteen runtime skills are now the stable contract; changes to
them from here on are versioned as breaking.

This is also the first release note in `docs/releases/`, so it carries the whole
0.x history that preceded it.

## What Changed In 1.0.0

The theme is the same one 0.2.4 and 0.3.0 started: every gate the rules claim
should be a gate the script actually enforces, and every rule it cannot enforce
should say so out loud.

### The record now distinguishes the user's decisions from the agent's

Every approval action — `execution`, `high-risk`, `git-action` — and the
`--reason` that closes a unit over an open verification are refused unless
recorded as `--actor user --status success`.

This is a deliberate ceiling, not proof: an agent can type `--actor user` as
easily as anything else. What it removes is the silent path. The default actor
no longer clears the gate, so recording a decision the user never made is now an
active lie in the record rather than an omission.

**Breaking:** any script or agent that recorded approvals with the default actor
now fails at `add`. Existing sealed records are unaffected — `validate` still
accepts them.

### Rule 7 gained the two halves the script could actually see

Approving execution now requires `plan.md` on disk, plus a review recorded with
`--phase write-plan --status success` that is newer than the previous execution
approval. A `review-execution` or `cleanup-code` review, or a plan review
recorded as an error, no longer satisfies rule 7 — the refusal message lists the
reviews it found and says why each one missed.

### `--resolves` became a general open/closed mechanism

`--resolves` now works for `blocker` as well as `verification`, is refused on
every other kind, and refuses to resolve a target something already resolved —
double-resolving would hide whichever gap is still open. `status --json` reports
open blockers through the same code path as open verifications.

### Two closing holes closed

- An `inbox` folder can no longer be finalized. The unit was never chosen, so
  there is nothing to declare complete: `move` it, or cancel it.
- A `topic` cannot finalize without `verification.md` on disk.

### Entry is strictly opt-in

`using-as-usual` no longer activates on an ordinary development or investigation
request. Only an explicit ask enters the workflow: the name, a `.as-usual/`
artifact, a resume request, or an owner skill invoked directly. When an
unrouted request would clearly benefit from a record, the skill says so in one
line and keeps working — once, at the point it notices, with no question and no
option list.

### `core-rules.md` states what the script cannot see

Three places where a rule holds only as a prompt are now named in the rules
themselves: `direct-work` completion that never calls `finalize`, the quality of
a `PASS` inside `verification.md`, and a git action chosen after the record is
sealed. A gate you believe in that is not there is worse than no gate.

### Documentation

`CLAUDE.md` stopped being a 305-line duplicate of `AGENTS.md`. It now references
it with `@AGENTS.md` and carries only Claude-host specifics — manifests, hook
config, the `.claude/skills/` mirror, install and reload. `AGENTS.md` gained the
release-note convention this file follows, and `publish-as-usual` requires the
note in the same commit as the version bump.

### Verified

`uv run --with pytest python -m pytest scripts/tests/ -q` — 131 passed ·
`ls skills/` is fourteen.

## Upgrading

Start a new session after updating — a running session never reloads plugin
state.

```bash
claude plugin marketplace update harness-as-usual
claude plugin update as-usual@harness-as-usual
```

Records written by 0.2.x and 0.3.0 remain valid and resumable. The only break is
forward-facing: new approval and close-over-a-gap entries must carry
`--actor user --status success`.
