Work folder

One kind of record. What it holds follows the request.

No label is chosen up front. Every record keeps the same two files; everything else appears only when the work needs it — and one record can hold all three outcomes, as when an investigation confirms a cause and then fixes it.

core rules §1
The work needsIt produces
requirements agreed first — ambiguous or risky workrequirements.md
a cause, direction, or feasibility established from code, logs, or an experimentconclusion.md, or it carries straight on into the change
a code changeplan.md, the change, and its verification
Requirements or investigation? If you know and the agent can just ask, it is requirements. If it has to be found in code, logs, or an experiment, it is investigation.
Size is not a criterion. Ambiguity and risk call for agreed requirements. A question answered by reading, or a single typo, needs no record at all.

Working in a git worktree
The change happens in the worktree…
…which can be removed once the work is done.
→
The project root is the main checkout
…the record lives in the main checkout
so it outlives the worktree.
$ dirname "$(git rev-parse --path-format=absolute --git-common-dir)"  # the project root
Your plan convention wins When the project has its own place for plans, the plan is written there and plan.md in the folder is a pointer to it.
Nothing here is committed .as-usual/ holds work records only. A deliverable for other readers — an API spec, a handoff note — goes where its audience looks.
No project-wide state No shared state.md, no shared audit.jsonl. Current state is derived per record with status --json.
Follow-up work: an investigation that carries on into the change stays in this folder. Work that is genuinely separate — a wider scope, a second deliverable, another repository — gets its own folder, linked both ways. If a linked record already exists, go back to it.
