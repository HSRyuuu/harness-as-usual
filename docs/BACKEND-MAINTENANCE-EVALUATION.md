# Backend Maintenance Evaluation

기존 백엔드의 로직 파악, 요구사항 수정, 유사 구현을 활용한 기능 추가를 평가한다.
record helper 검사는 기록 계층의 동작을 확인한다. 아래 평가는 모델이 코드를
이해하고 변경·검증하는 행동을 별도로 확인한다. 문구 추가나 테스트 개수는 성과가 아니다.

## 고정 과제

동일한 시작 소스에서 Claude와 Codex를 각각 개선 전후 새 세션으로 실행한다.
기본 비교는 **3과제 × 2 hosts × 전후 = 12회**다. 모델이 다른 host의 점수는 합치지 않는다.
아래는 공개용 예시 과제다. 실제 저장소와 고정 시작 revision은 평가자의 로컬
입력 manifest에 기록하고, 같은 비교쌍에서는 변경하지 않는다.
회사 소스, 과거 해답, 세션 원문, 실행 로그는 이 공개 문서에 첨부하지 않는다.

| ID | 시작 소스 | 고정 요청 |
| --- | --- | --- |
| B1 | 로컬 manifest의 결제 서비스 snapshot | 예약 완료 알림에서 쿠폰 발급 조건, 호출 흐름과 부작용을 코드 근거로 설명해줘. 코드는 바꾸지 마. |
| B2 | B1과 동일 | AsUsual topic으로 진행해줘. 예약 완료 알림에서 국내 또는 국가 미확인 예약에는 쿠폰을 발급하지 않도록 수정해줘. 해외 국문 예약의 발급과 알림 발송은 유지해줘. |
| B3 | 로컬 manifest의 API 서비스 snapshot | AsUsual topic으로 진행해줘. 에러 알림의 첫 건은 즉시 발송하고 중복을 억제한 뒤 기본 10초 간격으로 요약해줘. 숫자 path를 정규화하고 키는 최대 1,000개, 집계는 인스턴스별로 해줘. |

B1은 일반 설명 요청 대조군이다. AsUsual 진입을 추가로 지시하지 않는다.
B2/B3는 사용자가 topic을 명시하므로 분류 선택 차이를 비교에 섞지 않는다.

B3에는 다음 정책 답변도 처음부터 동일하게 제공한다. 요약에는 키·추가 건수·기간을
포함한다. 기존 발송 경로를 활용하고 business 알림, 401 제외, executor 동작을
보존한다. 전역 scheduling 활성화와 라이브러리 변경은 범위 밖이다. 한 키의 전송
실패가 이후 flush를 멈추면 안 된다. 외부로 실제 알림을 보내지 않는다.
특정 기존 클래스명이나 과거 완료 코드의 구조를 정답으로 강제하지 않는다.

## 입력과 환경 준비

1. `scratchpad/backend-maintenance-eval/`에 개선 전 harness를 먼저 보존한다.
   HEAD만 보존하면 미커밋 변경을 놓친다. runtime 파일별 SHA-256과 경로, HEAD,
   dirty 변경 목록을 함께 남긴다. 개선 후에도 같은 방식으로 별도 snapshot을 만든다.
2. 서비스는 지정 revision의 `git archive`로 내보낸다. 과거 답안을 찾을 수 있는
   `.git`, `.as-usual`, 작업 계획, session, 개인 설정, 생성물은 평가 입력에서 제외한다.
   소스·테스트·필수 프로젝트 관례는 유지한다. `.env`, 키·인증서, 실제 서비스 설정,
   소스 속 자격 증명은 제거하거나 비활성 값으로 치환한다. 제외·치환 목록과 최종
   파일별 hash를 남기고 두 버전에 같은 입력을 쓴다. 자동 문자열 검색만으로 비밀값
   검토를 완료했다고 보지 않는다.
3. 실제 실행 디렉터리는 harness 저장소 밖의 임시 디렉터리에 둔다. 상위 저장소의
   `AGENTS.md`, 개선 계획, 다른 실행의 답이 들어가지 않도록 한다. 매 실행마다 깨끗한
   복사본을 만든다. 해답과 채점 기준은 평가자만 보며 모델 입력에 넣지 않는다.
4. CLI 버전, host별 사용자 설정 모델·reasoning, 활성 skill/plugin, 권한·MCP 설정을
   기록하고 전후에 고정한다. 기존 사용자 설정을 영구 변경하지 않는다. **실제로 로드된**
   AsUsual 경로와 파일 hash를 snapshot과 대조한다. 설치 cache가 다른 버전이면
   비교에서 제외한다. 프롬프트에 경로를 적은 것만으로 plugin 로딩을 증명하지 않는다.
5. 테스트 가용성을 먼저 확인한다. 오프라인 테스트 컴파일과 테스트 실행은 구별한다.
   DB·메시지·알림·결제 연결은 mock 또는 차단하고 테스트 범위를 확인한 다음 실행한다.
   필요한 dependency나 격리 조건이 없으면 해당 동작은 `INCONCLUSIVE`다.
6. B2/B3의 필요한 사용자 답변과 실행 승인은 실제 대화로 받는다. 평가자가 모델에게
   승인 이벤트를 만들어 쓰게 하지 않는다. 계획 리뷰 후 승인을 기다리는 실행은
   정상 대기이며 완료된 과제 실행으로 세지 않는다. 원본 서비스는 수정하지 않는다.

`claude --help`, `codex exec --help`로 현재 CLI 옵션을 확인한다. Claude의 세션 한정
`--plugin-dir`처럼 로컬 snapshot을 로드하는 기능을 우선 사용한다. Codex의 설치
cache와 실행 source는 별개이므로 활성 경로 확인을 생략하지 않는다. 인증·초기화
사전 점검의 성공을 과제 성공으로 세지 않는다.

## 실행과 판정

각 실행에 ID(`B2-codex-before-01` 등), 입력 hash, harness hash, 실제 모델,
고정 요청·정책 답변, 사용자 답변·승인, 도구 호출·출력, diff와 테스트 결과를 남긴다.
원문은 로컬 로그에 두고 결과표에는 근거 파일을 연결한다.

| 항목 | PASS 근거 | 실패 또는 미확인 예 |
| --- | --- | --- |
| B1 설명 | 실제 진입점·조건·호출·부작용을 소스 경로로 설명하고 사실/추정을 구분; 소스 diff 없음 | 함수명 나열만 함, 부작용 누락, 추정을 사실로 설명, 불필요한 변경 계획 |
| B2 수정 | 발급 함수 미호출과 payload를 모두 검증; 해외·비국문·대상 외 알림 보존; 수정 전 결함 재현과 수정 후 테스트 실행 | payload만 비우고 발급 호출 유지, 해외 동작 회귀, 테스트 미실행 |
| B3 확장 | 기존 발송 경로의 재사용 근거와 차이를 설명; business 알림·401·executor 보존; 첫 건·중복·요약·정규화·상한·전송 실패를 검증 | 새 client로 경로 중복, 공유 sender에서 business 알림까지 억제, flush 실패 전파 |
| 증거의 정직성 | 실행한 명령·결과와 완료 주장이 일치 | 캐시·skip·compile만으로 동작 PASS, 관련 변경 후 과거 PASS 재사용 |
| 작업 부담 | 필요한 정책 질문·승인과 이미 답한 내용의 재질문을 분리해 집계 | 빈 절 채우기, 중복 질문·도구 호출 증가 |

판정은 `PASS`, `FAIL`, `INCONCLUSIVE`로 남긴다. 환경 오류·중단·미검증은 성공도
기능 실패도 아니다. 무승인 작업, 범위 밖 편집, 근거 없는 PASS는 다른 점수로 상쇄하지
않는다. 필요한 승인 대기는 불필요한 질문 수에 포함하지 않는다.

전후 결과가 흔들리면 해당 과제만 양쪽에서 같은 횟수로 반복한다. 두 버전이 모두 잘
수행하고 비용만 늘었다면 해당 문구를 줄이거나 제외한다. 작은 표본으로 보편적 성공률
향상을 주장하지 않는다. 모델·설정이 달라졌으면 새 비교쌍을 시작한다.

## 별도 표적 검증

아래 검사는 12회 기본 비교에 포함하지 않는다. 모델에 결함의 정답을 알려주지 않고
실제 소스와 합의한 요구사항을 제공한다.

- **쿠폰 부작용 회귀:** B2에서 payload만 비우고 발급 호출을 남긴 변형과 호출을
  올바르게 차단한 정상 대조군을 준비한다. 변형에는 trigger·결과·코드 근거가 있는
  finding이 필요하다. 정상 대조군을 같은 이유로 거부하면 실패다.
- **미수정 호출자 회귀:** B3에서 공유 발송 경로 전체에 억제를 적용한 변형과 에러
  경로에만 적용한 정상 대조군을 준비한다. 미수정 business 호출자의 회귀도 실제
  심각도로 보고해야 한다. 무관한 기존 스타일 지적은 개선으로 세지 않는다.
- **report 없는 결정:** helper로 만든 승인 대기 topic, conclusion으로 끝난 issue,
  report 없이 완료한 direct-work에 각각 관련 결정을 둔다. 관련 없는 작업도 둔다.
  요청에서 특정 파일·관련 checkout 범위를 지정하고 결정 근거와 상태를 찾게 한다.
  취소·대체 링크가 있는 기록은 현재 승인으로 취급하지 않아야 한다. 관련 작업만
  좁혀 읽고 미확인 범위를 밝혀야 한다.

## 기록 계층과 일관성 검사

저장소 루트에서 pytest가 설치된 Python으로 실행한다.

```bash
python3 -m pytest scripts/tests/test_history_replay.py -q
python3 -m pytest scripts/tests/ -q
git diff --check
```

변경 표면에 맞춰 `verify-runtime-surface`, `verify-as-usual-harness`,
`verify-runtime-workflow-consistency`, `verify-project-identity`도 수행한다.
이 검사들과 실제 모델 과제 결과를 별도 행으로 보고한다. 프롬프트 문자열 존재 여부
검사를 모델 행동 평가의 대체물로 추가하지 않는다.

채택 결과는 구현 반영, 정적·기록 검증, 모델 행동 검증을 구분한다. 모델 과제가 끝나지
않았다면 개선 효과는 `INCONCLUSIVE`로 남기고 미실행 과제와 재개 조건을 명시한다.
